# Reflection
Through this challenge, I learned the immense value of separating an algorithm’s logical design from the physical limitations of the hardware. The program required nested if‑else structures, a while loop with the distance sensor, and optical sensor detection to handle randomized room layouts. Testing the logic directly on the robot was frustrating because every run exposed different hardware errors—sensor readings drifted, motors sometimes didn’t engage consistently, and the physical environment introduced variables I couldn’t control. By building an HTML simulator that modeled an ideal virtual environment, I could trace the robot’s decision‑making step‑by‑step. This taught me that a well‑structured program, when stripped of real‑world noise, can be validated purely on its theoretical correctness, and that simulation is a powerful tool for algorithm development even before touching hardware. <br/>
The biggest challenge was the relentless hardware failures. The distance sensor occasionally returned wildly inaccurate values, the optical sensor would misread colors under slight lighting changes, and the robot’s movements were never perfectly repeatable. After hours of trying to tweak thresholds and recalibrate, I realized I needed to know whether my code was fundamentally flawed or the hardware was simply unreliable. I created an HTML simulator that represented the rooms, walls, and sensor readings with perfect accuracy. In this simulated world, my robot successfully visited all four randomized rooms using the same loop and if‑else logic, confirming that the algorithm would work in theory. Although I couldn’t get a perfect physical run, the experience taught me that isolating logic through simulation can pinpoint whether a failure lies in the design or the execution, and that documenting this process is just as valuable as a flawless demo.
